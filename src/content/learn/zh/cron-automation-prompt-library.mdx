“让 Hermes 在你睡觉时自动运行”是一个很有吸引力的方向，但 prompt 一旦写得太大，就会变成不可控自动化。好的 cron 任务应该有小范围、明确时间、明确投递目标，以及健康时保持沉默的规则。

## 先选任务形状

写 prompt 之前，先判断它是哪一类：

| 形状 | 适合场景 | 风险 |
|---|---|---|
| 简报 | 新闻、RSS、竞品、团队摘要 | 中 |
| 看门狗 | 磁盘、内存、服务健康、CI 状态 | 低到中 |
| 复盘 | PR、issue、过期任务 | 中 |
| 调研队列 | 选题发现、资料收集、阅读清单 | 中 |
| 纯脚本 | 阈值告警、心跳、状态检查 | 低 |

如果任务不需要推理，就优先用 no-agent 的纯脚本模式。只有真正需要综合判断时，才让模型参与。

## 提示词模式：每日简报

```text
每个工作日 08:30，收集本工作流已配置来源中的高价值 AI 基础设施更新。

返回：
1. 最重要的 5 条更新
2. 每条为什么重要
3. 我们应该考虑的一个动作
4. 来源链接

如果没有值得发送的更新，只回复 [SILENT]。
投递到飞书。
```

它有效的原因是：限制数量、定义格式，并且避免空转噪音。

## 提示词模式：仓库巡检

```text
每天 09:00，在 workdir /home/me/projects/acme 中检查打开的 PR 和 CI 状态。

返回：
1. blocker 优先
2. 需要人工 review 的 PR
3. 失败或不稳定的检查
4. 一个建议的下一步动作

不要修改文件。不要 approve 或 merge。
投递到来源会话。
```

`workdir` 让任务拿到项目上下文，prompt 里的限制把它保持在只读范围。

## 提示词模式：健康看门狗

```text
每 5 分钟检查 nginx 是否运行，以及磁盘占用是否低于 85%。

如果健康，只回复 [SILENT]。
如果不健康，报告：
1. 失败检查
2. 当前值
3. 人类应先运行的第一条命令

投递到 Telegram。
```

如果只是数值阈值检查，优先用 no-agent script，让 stdout 直接成为投递消息，不必调用模型。

## 提示词模式：调研队列

```text
每周一 10:00，从官方文档、社区文章和搜索趋势中收集 10 个 Hermes Agent 教程候选主题。

每个主题包含：
- 读者问题
- 来源链接
- 现有 playbook 是否已覆盖
- 建议内容类型：quick start、learn、template 或 troubleshoot

完整结果保存到本地，只把 Top 5 投递到飞书。
```

它有效的原因是：把完整调研输出和短通知分开，避免消息平台被长文刷屏。

## 高风险任务要加的边界

可以把这些句子加进 prompt：

```text
不要写文件，除非我明确要求。
不要给客户发送消息。
不要创建新的 cron 任务。
不要安装包。
如果缺少凭证，停止并报告。
```

Hermes 已经会避免 cron 内部递归创建 cron，但你仍然应该在 prompt 里写清任务边界。

## 生命周期命令

不要每次都删除重建任务。先学会暂停、恢复和手动触发：

```bash
hermes cron list
hermes cron pause <job_id>
hermes cron resume <job_id>
hermes cron run <job_id>
hermes cron edit <job_id> --schedule "every 4h"
```

最好的 cron 系统一定容易暂停。如果一个任务你不能快速停掉，它就还没准备好长期运行。
